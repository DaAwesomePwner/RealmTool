# RealmTool Phase 5 — UI shell and installer

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A per-user Windows installer for a Tauri 2 desktop app. The app runs the RealmTool Node backend as a supervised sidecar and offers:
- plugin cards with settings rendered from each plugin's schema;
- launch, proxy and helper controls with honest readiness indicators;
- a bounded live log;
- profile selection.

The installed footprint must be **≤ 120 MiB**.

**Architecture:** The backend gains five pieces:
- a resource-root resolver and an esbuild bundle (`backend/main.mjs`, `backend/worker.mjs`);
- an `AppController` that owns the proxy/plugin/helper lifecycle (it replaces the CLI's inline `runProxy`);
- serializable plugin snapshots;
- a bounded log store;
- an authenticated loopback HTTP + WebSocket API.

The Rust shell spawns a pinned `node.exe` with the bundle inside a kill-on-close Job Object. It hands the webview a per-launch token and supervises shutdown. The UI is a small Vite + TypeScript app with no framework. The headless CLI (`npm start`) keeps working and drives the same controller.

**Tech Stack:**
- Backend: Node ≥ 22.18 for development (TypeScript run directly); a pinned **Node 24 LTS** `node.exe` at runtime.
- TypeScript 5.9 with erasable syntax only.
- Build and test: esbuild (bundling), `ws` (the design's one permitted new runtime dependency), Vite + `happy-dom` (UI, dev-only), Vitest.
- Shell and installer: Tauri 2 (Rust 1.99, installed) with WebView2 (installed); the NSIS installer from the Tauri bundler.

**Spec:** [`docs/design.md`](../../design.md) §1 (budgets), §2.1 item 4, §2.4, §4, §5 row 5, §6 items 1 and 4. Research: [`docs/research/08-phase5-shell-details.md`](../../research/08-phase5-shell-details.md), cited as **R§n**. Background: [`docs/research/04-shell-ui-build.md`](../../research/04-shell-ui-build.md) (what to keep and drop from Realm Engine's dashboard).

## Global Constraints

- All Phase 1–3b constraints still apply:
  - `.ts` import specifiers, erasable syntax only;
  - `npm run check` green;
  - Windows x64 only;
  - RC4 keys only in `src/protocol/constants.ts`;
  - never start `RotMG Exalt.exe` directly (the launcher only);
  - the game access token is never logged, persisted, returned by the API or kept beyond its call;
  - time-critical decisions stay in worker modules. The UI and API change configuration only.
- **Every listener binds 127.0.0.1 only.** The game proxy stays on port 2050. The UI API uses an ephemeral port.
- **API authentication:**
  - Every HTTP request needs `Authorization: Bearer <per-launch token>`. The token is ≥ 32 random bytes, generated by the shell, and passed to the sidecar only in the `REALMTOOL_API_TOKEN` environment variable. The sidecar deletes it from `process.env` immediately after reading it, so the launcher and game never inherit it.
  - The `Host` header must equal `127.0.0.1:<port>`.
  - An `Origin` header, when present, must exactly match one in `REALMTOOL_UI_ORIGINS`.
  - Mutations are POST/DELETE with `Content-Type: application/json`. No state-changing GET.
  - The WebSocket authenticates with a one-use ticket issued by an authenticated POST: 30 s life, one connection. The upgrade also checks `Origin`.
- **Installed size ≤ 120 MiB**, measured on the installed files, excluding the shared WebView2 runtime. The plan pins Node 24 LTS (`node.exe` 93,580,104 bytes for 24.21.0, R§6). Ship only Koffi's `win32_x64` runtime. The "≤ 90 MiB headless" figure is not a v1 deliverable (ruling P4).
- **The dashboard source stays ≤ 3,000 lines** (UI `.ts` + `.css` + `.html`, design §1).
- The runtime dependencies are exactly `koffi` and `ws`. Everything else is a dev dependency. The installed app carries no `node_modules` except the trimmed `koffi` runtime and the bundled code.
- Ported or adapted files keep their provenance header. New files need none.
- No auto-updater, no account or credential features, no server-switch dropdown, no overlay (design §1 non-goals).

## Rulings (the controller's; U1–U5 approved by the user on 2026-10-04)

Each ruling ends with what it costs if it turns out wrong.

- **U1 Node runtime: pin Node 24 LTS** (24.21.0 at writing). It's 89.2 MiB, against 98.4 MiB for the local Node 26. Node 22 saves another 6 MiB but reaches end of life in April 2027. *Cost:* ~6 MiB of headroom versus Node 22.
- **U2 Profile switching is restart-based.** Selecting a profile saves `activeProfile`, stops plugins and the proxy, then starts them again with the new profile. A connected game is disconnected, and the UI asks first. There's no live transactional switch (3a ruling 5 stands). *Cost:* switching profiles mid-game drops the connection.
- **U3 Helper lifecycle unchanged from the CLI.** Starting the proxy installs or updates the helper (backing up a foreign `winhttp.dll`). Quitting leaves it installed. The UI has an explicit "Uninstall helper" button, and the uninstaller removes the helper and restores the backup. *Cost:* Realm Engine stays blocked until the user uninstalls (design §6 item 4).
- **U4 WebView2: `downloadBootstrapper`** (Tauri default). The budget excludes the shared runtime, which Windows 10/11 already ship. *Cost:* a machine without WebView2 needs internet during install.
- **U5 Install scope: per-user** (`currentUser`, `%LOCALAPPDATA%`, no admin). *Cost:* each Windows user installs separately.
- **P1 The shell spawns the sidecar from Rust** (`std::process::Command` plus a Windows Job Object with `KILL_ON_JOB_CLOSE`). There's no `tauri-plugin-shell` and no JS-side process capability. *Cost:* a little more Rust.
- **P2 Window close hides to the tray while the proxy runs. Otherwise it quits.** The tray has Show and Quit. Quit runs a graceful shutdown: `POST /api/shutdown`, wait up to 3 s, then the Job Object kills the sidecar. *Cost:* users can miss that the app is still running; the first hide shows a one-time notice.
- **P3 Sidecar handshake on stdout:** a single line, `REALMTOOL_READY {"port":<n>}`. Everything else on stdout and stderr is discarded by the shell (logs go to the log store and file). The sidecar exits when its stdin closes (the shell died) or on `POST /api/shutdown`. *Cost:* none expected.
- **P4 Headless budget.** The design's "≤ 90 MiB headless" can't be met with any supported Node (`node.exe` alone is 83–98 MiB). v1 ships only the UI package. T10 updates design §1. *Cost:* a docs change.
- **P5 Plugin UI is schema-driven only.** No per-plugin custom views beyond generic status rendering: key/value status from `data.status`, Chat Filter `recent` as a text list, Auto Nexus/Auto Drink state lines. *Cost:* plain-looking status panels.
- **P6 Logs.** In memory: a 1,000-record ring. On disk: `%APPDATA%\RealmTool\logs\realmtool.log`, rotated at 1 MiB, keeping 3 files. Sinks are isolated, so a throwing sink is dropped with one console warning. *Cost:* older logs roll off.

## Review Focus

1. **A browser page or another local process tries to drive the API.** Requests without the bearer token, with a wrong `Host`, a foreign or `null` `Origin`, form-encoded bodies, a reused or expired WS ticket, or the token in a query string are all rejected (401/403), with no state change. Pinned in Task 5.
2. **The shell crashes or is killed.** The sidecar and its worker exit (Job Object plus stdin EOF). The game proxy port is freed, and a restart works. Pinned in Tasks 8 and 10.
3. **The UI is closed or the profile switched while a game is connected.** Plugins flush their profile writes, worker modules get `configure(enabled:false)` on stop, and no half-applied profile is left behind. Pinned in Tasks 2 and 6.
4. **Packaged resource paths.** In the installed layout, every data file, catalog, the helper DLL and the worker resolve from the resources root, and nothing references `.ts`, `src/` or `node_modules` outside the trimmed Koffi. Pinned in Tasks 1 and 9.
5. **Plugin settings from the UI.** Each plugin's own validation decides. Values a plugin clamps (for example Auto Nexus thresholds) are accepted, and the stored value is shown. Values a validator rejects (wrong type, out of range under generic validation), unknown or hidden keys, and a button on a disabled plugin are rejected with the validator's message, and don't change the profile. Accepted changes reach the worker exactly as the CLI path does (for example Collision HP off). Pinned in Tasks 3 and 5.
